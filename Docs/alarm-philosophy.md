## 0. 这份文档在流程里的位置

GB/T 41261 把报警系统当成有生命的东西：生命周期七阶段转成一个环，**第 1 阶段的产出物就是这份《报警哲学》**（摘要 §3.1）。它是整个生命周期的第一块多米诺——没有它，优先级退化成「谁嗓门大谁高优」，合理化评审会开成吵架会。**先立规矩，再回炉清单，顺序反了就是吵架会。**（摘要 §3.3）

本文档是**框架哲学**：管 Framework.Alarm 模块（ADR-0009 确认新建顶层能力库，ADR-0010 定为家族两件套：引擎 + Domain/Infrastructure）在代码里强制什么、随附什么默认值、把什么留给宿主。宿主程序（具体产线）在这套机制上再写自己的**工艺哲学**：具体的严重度分档、响应时间分档、限值数值、保留期。双层各管各的，改动都留痕。

验收对应：本文就是验收清单第 2 项要的「《报警哲学》v0.1+（判据/分档/配比/搁置规则/保留期）」（摘要 §10）。

## 1. 目的与范围

**管什么**【强制】：

- Framework.Alarm 能力库的设计依据：报警引擎、事件历史库、KPI 聚合、呈现接缝的行为准则；

**给谁看**：模块维护者（引擎契约）、宿主程序作者（使用规则）、合理化评审参与者（判据）。

## 2. 报警判据

### 2.1 定义【强制】

> **报警**：通过声音和/或可视的手段，向操作员指示**需要及时响应**的设备故障、过程偏差或其他异常情况。（摘要 §2.1【标准】）

最锋利的限定词是「**需要及时响应**」——报警不是记录、不是消息，是**派给操作员的一份限时行动指令**。两个直接推论：

- 给维修/质量工程师的数据走报表与事件，**不进报警通道**（行动者不是操作员）；
- **最低优先级的报警仍是报警**，照样挤占注意力——没资格当报警的信息降级为事件/提示，不配成低级报警。

### 2.2 报警判定三问【强制】

候选「报警」的准入流水线，三个条件缺一不可（摘要 §2.2【标准】）：

1. **需要操作员行动吗？** 不需要 → 不是报警（留痕的进事件，告知的进提示）；
2. **要在限时窗口内行动吗？** 拖过窗口有后果（报废/损坏/停产）→ 报警；只是「尽快关注」→ 提示；
3. **操作员知道该干什么吗？** 答不出下一步 → 先补操作指引，否则不算合格报警。

三问同时是 KPI 聚合前的统一过滤器（§8.2）。

### 2.3 三分类去向【强制】

| 分类 | 判据 | 去向 | 常见误配 |
|---|---|---|---|
| **报警** | 异常 + 操作员行动 + 限时窗口 | 报警列表、声光提示 | 温度超限被埋在一堆记录里 |
| **事件** | 留痕追溯，无需响应 | 历史记录 / 操作日志 | 启机、改参数被配成「低级报警」 |
| **提示** | 需关注，无需限时响应 | 状态栏 / 消息中心 | 「磁盘不足」天天弹窗骚扰 |

（摘要 §2.3【标准】）报警泛滥的根源几乎从来不是「异常太多」，而是大量事件和提示挤进了报警通道。

### 2.4 事件 ≠ 日志【强制】

**事件是内容，日志是本子**：报警要人做事，事件陈述发生，日志负责记本子。报警的每一次状态变化都作为事件写进历史——不是「日志属于报警」，而是「报警的生命周期靠事件记录留痕」（摘要 §2.4）。

## 3. 引擎行为契约

本节把标准的口头规矩写成引擎的可测试契约。总纲：**判定权只许住在引擎层**——表现层只呈现、采集层只报事实，谁越界谁就是在再造「看情况定义」（摘要 §8.2）。

### 3.1 四状态五转换【强制】

| 当前状态 | 事件 | 去向 | 系统行为 |
|---|---|---|---|
| Normal 正常 | 条件越限 | **未确认** | 声光起，进报警列表，事件入库 |
| 未确认 | 操作员确认 | **已确认** | 由闪变稳，责任接管 |
| 未确认 | 条件恢复 | **RTN**（恢复未确认） | 闪绿，仍留列表等确认 |
| 已确认 | 条件恢复 | **Normal** | 移出列表 |
| RTN | 确认恢复 | **Normal** | 移出列表，闭环 |

（摘要 §4.2【标准】）

**RTN 口径是已核实的最高优先级保真项**（摘要 §4.3【标准】）：RTN 只从「未确认」进入（auto-reset）；已确认的报警条件恢复**直接回 Normal**——「有主人的报警，回家不用再敲门」。RTN 存在的理由：半夜触发、凌晨自愈、没人开过界面的报警不悄悄蒸发，闪绿留列表，等人补一个「看见了」。

### 3.2 呈现纪律【强制】

- 状态显示惯例（ISA-18.1）：未确认=闪红、已确认=稳红、RTN=闪绿（摘要 §4.4【惯例】）；
- 三态样式**绑引擎流转的 State，不绑「当前值与限值的差」**——UI 一比较数值，判定权就漏出去了；
- 排序置顶按档案 Priority；详情弹窗 = MADB 档案原样呈现，操作动作放最显眼处（第三问在这一屏兑现）。

### 3.3 锁存【默认】

锁存（latch）= 条件恢复也不自动灭，须人工复位，等的是「复位授权」——与 RTN 等「确认看见」不是一回事，别混淆（摘要 §4.3）。**已拍板：v1 不做锁存**（§12 #2），联锁/停机类宿主需求留到 v2。

### 3.4 两条沉默决策【强制】

摘要 §8.7，测试逼出来再定型的契约：

1. **无档案不报警**：采集层报来的条件若没有 MADB 档案，直接忽略——「先立档案再报警」，倒逼每条报警有出生证；
2. **报警中不重播**：采集层每秒报值，状态机保证 `Raised` 只发一次（非 Normal 状态时触发无效——Normal 时触发是唯一入口）。

### 3.5 活跃列表与历史库【强制】

- **活跃列表 = 事件流的读模型投影**，不是第二份真相；成员 = 未确认 + 已确认 + RTN；已确认后恢复的移出（摘要 §8.9）；
- **事件历史库 append-only**，只进不改——改历史 = 毁证据（摘要 §8.11）；
- 未被看见的恢复（`AlarmAutoReturned`）与真正闭环（`AlarmClosed`）**记成两种事件**——早班的「昨夜发生过什么」靠这条区别（摘要 §8.5）；
- 非法转换（如 Normal 时确认）**静默忽略**——不改状态即返回【已拍板：#9 状态机 TDD 落定，ADR-0009 规则 9 兑现】：采集层每秒报值、操作员命令有竞态，非法调用是高频竞态噪音，不是程序错误；原则不变——不得破坏状态一致性与历史完整性。

## 4. 优先级体系

### 4.1 分级【强制】

固定三级：**高 High / 中 Medium / 低 Low**（分级数量 3~4 级封顶，摘要 §3.3）——引擎随附的 `Priority` 枚举即三级（§12 #1 拍板）。宿主要四级须先改框架、走 ADR。

### 4.2 矩阵机制【强制】与默认分档【默认】

铁律：**优先级查矩阵，不凭嗓门**——由后果严重度 × 最大响应时间（MTR）推出来，矩阵坐标记入档案（摘要 §5.2）。

机制：`Priority = Matrix(Severity, MaxResponseTime)`。

默认分档（**占位示例，宿主必须按自家工艺重定义**——摘要 §5.2 明令教学矩阵不得照抄）：

- 严重度：S1 人身安全/重大环境；S2 停产/设备损坏；S3 质量/产量/经济性；
- 响应时间：T1 ≤5 分钟；T2 5–30 分钟；T3 >30 分钟。

| 示例矩阵 | T1 需立即处理（≤5 分钟） | T2 需尽快处理（5–30 分钟） | T3 可计划处理（>30 分钟） |
|---|---|---|---|
| **S1** 人身安全 / 重大环境 | 高 | 高 | 中 |
| **S2** 停产 / 设备损坏 | 高 | 中 | 低 |
| **S3** 质量 / 产量 / 经济性 | 中 | 低 | 低 |

读法要点：S1 一路高，只在响应窗很宽时降为中——安全后果从不含糊；时间窗越短，优先级越高。

### 4.3 配比目标【默认】

| 高 | 中 | 低 |
|---|---|---|
| ~5% | ~15% | ~80% |

多源一致的行业目标（EEMUA 191 基准）。配比失衡的信号：高优先级超过一成——「狼来了」常态化，真正的高报警失去区别度。配比是合理化质量的年检项（摘要 §5.3）。

## 5. 命名与描述规范

- **位号 Tag**【强制】：全系统唯一；格式宿主自定，但必须稳定、能从位号定位到设备（摘要示例 `HEAT01_TEMP_HI`）。
- **描述**【强制】：一句话说清**发生了什么**，含方向（高于/低于）。怎么办写在操作动作栏，不由描述栏承载。
- **操作动作必填**【强制】：填不出操作动作的候选**当庭退回**——要么不是报警，要么先把指引补上（摘要 §5.4）。
- 文案不做判定、不夸大、不软化：严重程度由优先级与呈现承载，不由形容词承载【默认】。

## 6. 主报警数据库与组态整定

### 6.1 MADB 字段清单【强制】

合理化阶段的法定产出——每条报警的出生档案（摘要 §5.4，字段为多源共识清单）：

| 字段 | 填什么 | 示例 |
|---|---|---|
| 位号 Tag | 全系统唯一 ID | HEAT01_TEMP_HI |
| 描述 | 发生了什么（一句话，含方向） | 加热板温度高于工艺上限 |
| 分类 | 安全 / 环境 / 设备 / 工艺 | 工艺 |
| 不处理后果 | 放着不管会怎样 | 本炉产品全部报废 |
| 最可能原因 | 排查起点 | 加热管失控或热电偶漂移 |
| 操作动作 | 第三问的答案：第一步干什么 | 停炉切手动，通知工艺员 |
| MTR 最大响应时间 | 后果发生前的窗口 | ≤5 分钟 |
| 严重度档 | S1 / S2 / S3（按宿主哲学） | S2 |
| 优先级 + 依据 | 查矩阵的输出，**附坐标** | 高（S2 × T1） |
| 组态参数 | 限值 / 死区 / 延时（§6.2） | 限值 250℃ / 死区 2℃ |
| 评审留痕 | 评审人 / 日期 / 哲学版本 | 张三 2026-09-30 v0.1 |

代码投影 = `AlarmDefinition` record（摘要 §5.5）。存储 v1 定 SQLite（§12 #4 拍板），读写走存储接缝，引擎不直连数据库（摘要 §8.4 `IAlarmDefinitionStore`）；实现为报警家族 `Framework.Alarm.Infrastructure` 的 EF Core——SQLite 引擎不变，裸 SQLite 手写实现退役（ADR-0010）。

### 6.2 组态参数整定【强制】

| 参数 | 作用 | 整定原则 |
|---|---|---|
| 限值 setpoint | 触发点 | 来自合理化（工艺依据），不是出厂默认 |
| 死区 deadband | 恢复点 = 限值 − 死区 | 略大于信号噪声幅值 |
| 触发延时 on-delay | 越限持续满 X 秒才报警 | 略长于毛刺时长，且 < MTR |
| 恢复延时 off-delay | 条件恢复满 X 秒才清 | 条件在限附近抖动时才需要 |
| 分组 group | 按区域/工段/模式归类 | 支撑画面过滤与停机态批量抑制 |
| 显示呈现 | 颜色/声音/列表位置 | 按优先级（§3.2） |

（摘要 §6.5）

**两条铁律**（摘要 §6.3【标准】）：

1. **触发延时 < MTR**——响应窗口从条件越限起算，延时先吃掉一截；
2. **死区 ≥ 信号噪声幅值**——太小等于没设。

**参数有意化**（摘要 §6.4【标准】）：标准不定死具体数值，只规定这些参数必须被**有意选择、整定依据记入档案**。每个旋钮的选择都要能回答：**我因此对什么视而不见？** 不允许「出厂默认裸奔」。

**颤抖与鉴别诊断**：颤抖判据 = 同一来源 60 秒内 ≥3 次状态转换（摘要 §6.1【标准】）。它是**探测器不是诊断书**——先看恢复值再开药：压线恢复、秒级活跃、没来得及确认 = 设计病（死区太小/限值落在振荡带），加大死区或挪限值；深度回落、完整处理周期、每次都有确认 = 根因病（修根因，短期修不了走限时搁置）。**别因「烦」放宽限值**——会把真复发也放走，是「删报警后门」的另一种形态。治理的终点不是零报警，是**剩下的都是真报警**（摘要 §6.6）。

## 7. 搁置与屏蔽规则

三种「合法闭嘴」【强制】（摘要 §4.5）：

| | 搁置 shelving | 运行态抑制 suppression | 退出服务 out-of-service |
|---|---|---|---|
| 谁发起 | 操作员（现场） | 组态逻辑（设计态） | 工程/维护 |
| 时限 | **必须有**，到期自动恢复（常以一个班次为上限） | 随设备状态自动生效/失效 | 到检修结束 |
| 审批 | 即时，但全量留痕 | 走组态变更 | 变更管理（MOC） |
| 可见性 | 主列表移除，**搁置清单单独可见** | 对操作员不可见（按设计） | 退出服务清单可见 |
| 典型场景 | 吹扫期间某液位计乱报 | 停机时不报「运行参数异常」类报警 | 检修某仪表，相关报警长期退出 |

三条规矩（摘要 §4.5、§8.10）：

- **搁置必须限时**【强制】——无限期搁置 = 变相删报警；要长期闭嘴的走退出服务 + 变更管理；
- **引擎机制：搁置 = 事件打标（`ShelvedUntil`），不拦状态机**【强制】——搁置期间条件照常触发、状态照常流转、事件照常落库；UI 按标过滤主列表；搁置清单 = `Active.Where(ShelvedUntil > now)`，单独可见；到期不用定时器解除——时钟一过，标自然失效；
- **全量留痕**【强制】——三种闭嘴的所有动作都进历史库。共同意义：给合法的闭嘴留正门，堵死「删报警」这个后门。

## 8. 事件历史与 KPI 目标

### 8.1 事件历史【强制】与保留期【待拍板】

- append-only，订阅即入队、后台冲账：引擎产出的每一拍自动进本子，包括带搁置标的（摘要 §8.11）——落库在后台单写者手里按进队次序逐条来（本子次序即履历次序），引擎产事件的线程不等落库（#31，ADR-0011）；代价是进程在冲账前崩溃时队列尾部事件丢失（履历完整性与冻屏之间拍板选不冻屏）；
- 保留期【默认】：**90 天**（行业常见 90 天～1 年，宿主按追溯要求定）——§12 #3 拍板确认；
- 存储：SQLite 单机，经存储接缝访问——§12 #4 拍板；实现为家族 EF Core，建库走迁移（90 天历史要跨版本存活，ADR-0010）。

### 8.2 七项 KPI【默认】

目标值来自 EEMUA 191 基准，行业经验值非法定值，宿主可收紧或放宽但要有意为之（摘要 §7.1）：

| 指标 | 定义与算法 | 默认目标 | 超标后查什么 |
|---|---|---|---|
| 平均报警率 | 报警总数 ÷ 小时数（每操作员口径） | ≤6 条/时 | 非报警混入（三问复查）、颤抖源、泛滥源 |
| 峰值（10 分钟桶） | 任一 10 分钟桶内最大报警数 | ≤5 条；10 条是可管理上限 | 停机/扰动瞬间的连锁触发（分组+抑制） |
| 泛滥 flood | 10 分钟 >10 条即泛滥；统计泛滥时间占比 | 时间占比 <1% | 泛滥源回放：第一条是什么、哪些跟着哄 |
| 优先级配比 | 高/中/低占比（年检） | ~5% / ~15% / ~80% | 评审会是否被嗓门劫持（回查矩阵坐标） |
| 颤抖 chattering | 同一来源 60 秒内 ≥3 次转换 | 0 台 | 死区/延时，或限值已过时 |
| 驻留 standing | 活跃持续 >1 小时 | 0 条（现实 <5） | 该条件是常态？→ 回合理化降级为事件/提示 |
| 陈旧 stale | 活跃持续 >24 小时 | 0 条（现实 <5） | 变更管理失守的信号——限值/设备早变了 |

**关键性质**【强制】：七项全部从事件历史库算出，数据源只有一个；聚合前先按三问分类过滤——体检对象是报警不是事件，混进一批「启机记录」平均率直接失真（摘要 §7.1）。

### 8.3 体检节奏【默认】

| 频率 | 动作 | 谁 |
|---|---|---|
| 每班 | 看板 1 分钟：昨日总数、当前泛滥/驻留数 | 操作员/班长 |
| 每周 | Top-10 最响仪器排行 + 颤抖清单跟踪归零 | 报警负责人 |
| 每年 | 全量 KPI 评审 → 修订哲学 → 触发回炉 | 评审会 |

（摘要 §7.2）

## 9. 角色与职责

**框架侧**：

- 模块负责人【强制】：维护引擎契约与本哲学的一致性；KPI 机制的正确性；
- 呈现层作者【强制】：只呈现不判定——每条呈现规则必须来自引擎产出或档案字段。

**宿主侧**：

- 报警负责人【默认】：每条报警有主，扛每周 Top-10 与颤抖归零节奏；
- 评审会【默认】：工艺 + 操作 + 仪表/控制共同坐席，负责新报警准入与回炉评审；
- 操作员【强制边界】：可以确认、可以限时搁置；**无限期闭嘴不走操作员通道**（那属于退出服务 + 变更管理）；
- 每条报警在 MADB 里必须能回答「负责人是谁」——无主报警当庭退回。

## 10. 评审流程

**新报警准入（合理化）**【强制】（摘要 §5.1）：

> 三问过资格 → 不处理会怎样（后果）→ 操作员第一步干什么（动作）→ 有多少时间（MTR）→ 查矩阵定优先级（附坐标）→ 入 MADB（评审留痕：评审人/日期/哲学版本）。

**回炉触发**【强制】（摘要 §3.2）：

- 工艺、设备、程序一有改动，相关报警拉回环里重评审（变更管理）；
- KPI 年检偏差大（配比失衡、颤抖未归零、驻留/陈旧超标）→ 回合理化；
- 遗产报警是环存在的原因：设备和工艺在变，报警没跟着变，就会永不触发（假安全感）或乱触发（新刷屏源）。

**存量改造进场**【默认】（摘要 §8.12，宿主项目四步迁移）：只建历史库拿 KPI 基线（零风险）→ 档案+引擎影子模式并行 → 按工段切 UI、老报警逐条退役 → KPI 看板常态。
