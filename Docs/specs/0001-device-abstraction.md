# 设备抽象层：按厂商适配器统一驱动相机与运动控制卡

## Problem Statement

工业上位机需要驱动不同厂商的硬件（相机、运动控制卡等），各厂商 SDK 私有不兼容。当前代码里 `CameraHikVision` 是一具骨架：接口直接照搬海康 SDK 的参数模型（字符串键 `SetFloatValue("ExposureTime", …)`）、原始 SDK 对象以 public 字段外泄、图像以 `IntPtr` 与非托管内存直接暴露，且没有"根据数据库配置在启动时加载不同 DLL"的机制。上层应用硬编码 `new CameraHikVision()`，换一个厂商就得改代码重编译。

## Solution

建立三层设备抽象：极薄的 `IDevice` 作根，`ICamera` / `IMotionCard` 按设备类型细分，每个厂商一个适配器类、各封装自家 SDK。上层只面对一个强类型最小契约；启动时按数据库配置 `(设备类型, 厂商, 连接方式)` 动态加载对应厂商适配器的 DLL。图像以 `byte[]` 为规范表示。

## User Stories

1. As 上位机应用，I want 通过统一的设备接口打开/关闭任意厂商的相机，so that 上层代码完全不感知具体厂商。
2. As 上位机应用，I want 一个强类型的最小相机契约（取图 / 曝光 / 增益 / 软触发 / 开始停止采集），so that 我不需要记忆厂商私有的字符串参数键。
3. As 算法开发者，I want 从相机拉取一帧图像，以托管字节数组 + 宽高 + 像素格式返回，so that 我能直接把帧喂给视觉算法而不处理非托管内存。
4. As 上位机应用，I want 一个实时的图像通道做连续预览，so that 画面能低延迟刷新。
5. As 设备集成工程师，I want 在数据库里为一台设备配置设备类型、厂商和连接方式，so that 程序启动时自动按配置加载正确的适配器。
6. As 设备集成工程师，I want 用 TCP（IP 地址 + 端口号）或 COM（串口号）描述连接方式，so that 不同传输方式的设备都能接。
7. As 设备集成工程师，I want 新增一个厂商等于放一个适配器 DLL 加一条配置记录，so that 不用重编译整个程序。
8. As 上位机应用，I want 启动时按配置加载并实例化正确的厂商适配器，so that 不需要在任何地方硬编码厂商。
9. As 设备集成工程师，I want 同一类型同一厂商的多台设备各自独立配置，so that 一条产线上的多台相机 / 多块运控卡各连各的。
10. As 现场操作员，I want 某台设备连接失败时程序降级运行（记录错误但不拖垮整机），so that 单点故障不中断整条产线。
11. As 设备集成工程师，I want 连接失败时得到分类明确的错误（没找到设备 / 打开失败 / 参数不支持），so that 我能快速定位是接线问题还是配置问题。
12. As 上位机应用，I want 运动控制卡也挂在同一套设备抽象下，so that 相机和运控卡被一致地发现、打开、关闭。
13. As 上位机应用，I want 程序退出时统一关闭所有已打开的设备，so that 不遗留连接与资源。
14. As 现场操作员，I want 设备可以关闭后重新打开（重连），so that 现场维护不必重启程序。
15. As 算法开发者，I want 相机曝光时间与增益用强类型参数设置并读回，so that 调参不必翻厂商 SDK 手册。
16. As 设备集成工程师，I want 把厂商私有的底层参数操作（如用户配置集 UserSet）从上层契约里隔离，so that 上层契约保持最小。
17. As 上位机应用，I want 通过设备标识（而非具体类型）取得已初始化的设备，so that 配方或流程只需引用一个逻辑设备。

## Implementation Decisions

- **三层抽象**：`IDevice`（极薄：名称 / 打开 / 关闭）→ `ICamera`（相机契约）、`IMotionCard`（预留）→ 厂商适配器（海康相机适配器等）。
- **相机契约（强类型，无字符串键）**：打开 / 关闭（继承自设备）、开始采集 / 停止采集、取一帧、设曝光 / 读曝光、设增益、软触发；另有实时图像通道。
- **图像表示**：图像数据以托管字节数组 + 宽度 + 高度 + 像素格式为规范，移除裸指针与厂商枚举泄漏。
- **厂商适配器**：每个厂商一个类，封装自家 SDK，把强类型调用翻译成 SDK 私有调用；原始 SDK 对象不外泄。
- **设备管理器**：读配置 → 用 `(设备类型, 厂商)` 查注册表 → 加载适配器 DLL → 实例化 → 按连接方式打开；统一维护设备生命周期（含退出时统一关闭）。
- **配置实体**：设备级配置，字段为设备类型（相机 / 运动控制卡 / 其他）、厂商、连接方式（TCP / COM）、TCP 地址、端口号、COM 口号。与现有配方参数中的相机引用是两回事，需厘清边界。
- **运行时插件加载**：厂商适配器为独立程序集，启动时按配置动态加载，不硬引用。
- **错误处理**：适配器把厂商错误码翻译成统一的错误类别，供上层判读与降级。
- **启动接入**：在主程序初始化阶段接入设备管理器。

## Testing Decisions

- **好测试的标准**：只测外部行为，不测实现细节；用假适配器替换真实硬件与厂商 SDK。
- **测哪些模块**：① 相机契约（用假适配器验证契约行为）；② 设备管理器（内存配置 → 解析出正确适配器，不加载真实 DLL）。
- **不测**：真实 SDK 调用与真实硬件（需人工在有硬件环境验证）。
- **既有先例**：现有的错误码映射测试思路可沿用；但现有的"死循环测试"和"断言未实现成员抛异常"的契约测试要重做，改为验证真实契约行为。

## Out of Scope

- 运动控制卡的具体控制契约（本规格只预留抽象层与配置类型）。
- 视觉算法实现与图像处理。
- UI 层（预览画面、设备配置界面）。
- 厂商 SDK 适配器的内部实现细节（由各适配器工单单独负责）。
- 真实硬件的自动化测试。
